# Central Team-scope admission — implementation blocked on durable scope

This is an implementation design for pinned public source `b830ec950faba0a46dda564be3e2d854afed94f1`. **No central authority, scope writer, migration or complete R1/R2 enforcement is enabled.** The Team-only source patch and shape checker in this directory are separately labelled experiments and cannot be combined into a trustworthy authority by passing a caller flag or a synthetic verification callback.

## Native evidence for the missing discriminator

Three **unmodified pinned-source synthetic Host tests** were rerun: ordinary forks become new implicit Team roots; ordinary non-Team subagents have `tryMembership() === undefined`; and a cold-resumed orphaned provider child or a child whose parent Team stream is malformed also has `tryMembership() === undefined`. All three passed, 41 other tests were not run. Retained `work/team-scope-evidence/pinned-scope.log` SHA-256 `e73bccb95abf349005db92170d91cec83f35d8e554dc5988e4d56b41f6485966`; matching pre/post source, test and local native-addon manifest SHA-256 `f94ec8ea529c1c9490161b5b7799a2c21a4a3c1a051298860651024bf4811cd0`. Tests used synthetic Sessions, mock model and task-owned TMPDIR, not a real user profile. This result confirms `undefined` is not a safe synonym for non-Team.

The pinned roster also treats a top-level Agent as an implicit Lead before it has any Team record. A separately retained grant-WIP canary shows a fresh ordinary root and a prospective Team root have identical Lead classification and no member record. Thus neither `tryMembership()` nor absence of `team/member` can distinguish the two at the exact time a central gate must decide. `SessionHeader.parentSession`, `origin`, and `delegationDepth` do not solve this: forks and subagents have different semantics, `origin` is documented as coarse presentation metadata, and absolute depth is not a Team-relative budget.

## Required Host-owned scope model

The genuine shared owner must resolve every relevant caller into one of **verified Team scope**, **verified explicit non-Team scope**, or **unknown**. It must use exact live Agent/Session identity plus a committed, versioned Host-owned scope/lineage record, not request flags, tool arguments, optional callbacks, copied IDs or absence of a record. An unknown Team-capable scope fails closed; a verified non-Team scope preserves the existing provider-managed semantics. Host-side classification must be established at creation or migration and attached to all subsequent descendant creation paths. The existing code has no authenticated way to make that distinction for all legacy roots.

A minimal required Team node record must identify its version, exact node/Session, Team root and immediate Team-parent, relative level, Team epoch, effective policy revision and durable parent/admission reference. A corresponding explicit non-Team identity must not be forgeable by an Agent or model. The owner validates no cycles, uniqueness, parent/root consistency and hard root-plus-three-level ceiling. For a Team, the user clarified that the global value is the default and a Team override replaces that default for that Team; nested-ancestor override composition and its interaction with the pre-existing absolute subagent limit still need an explicit compatibility rule. Missing, conflicting, malformed, untrusted, stale, partly migrated or unavailable lineage remains UNKNOWN.

An opt-in `prePublish` callback is inadequate: direct and workflow paths can omit it, as the actual synthetic direct-activation bypass test shows. A central `SubagentRuntime.startActivation` guard must resolve scope independently, and every route able to create a Team descendant must pass the same owner. Audit the manager's local and external paths, Team, `tool-subagent`, workflow PTC and any direct Agent factory/host tool paths; an external provider must supply a separately verified enforceable policy or Team-scoped use is denied. Do not impose a new blanket limit on verified non-Team `provider-managed` work.

## Publication, migration and recovery blockers

The manager calculates child depth before asynchronous directory/provider preparation. A retained Host test shows a Team spawn admitted at limit 1 can complete after that limit becomes 0. A real owner needs durable versioned permits and common serialization of policy changes with the actual final publication/initial-message acceptance boundary. Under the user's provisional policy, a reduction fences **unpublished** admissions; already-published children are not silently killed. Cross-process writers need proven CAS/fencing or a durable single writer; provider/materialization side effects before publication need explicit rollback/unknown state. A WeakMap, a per-process queue or a check before an `await` is not enough.

The released V4 Team projection rejects both a new version of the existing `team/member` event and extra lineage fields in the v2 payload. A required new event is rejected by the pinned old V4 JSONL reader in a synthetic read/write test. Making the event ignorable would let old readers omit security-relevant scope and is not suitable for admission. Versioning, adjacent migration, old-reader refusal, mixed old/new generation selection, backup and rollback must be designed before writing any real scope record. Historical V4 roots and descendants with incomplete Team evidence cannot all be safely classified as non-Team; they remain blocked for Team-scoped admission until an authorized migration/reconciliation proves their scope. Do not silently discard or rewrite records to obtain a result.

The existing backend retains prior physical generations but selects the highest canonical one, so retention is not automatic downgrade. A migration must publish an independently validated successor, preserve a verified pre-upgrade copy, and account for later writes during any rollback. A cold restart must reload and authenticate scope, Team policy revision and unresolved admission receipts before permitting a spawn; absent or corrupt policy is deny/UNKNOWN, not a default grant.

## Exit tests

Implement only after the scope source and migration are agreed. Synthetic Host tests must cover Team, direct, workflow and tool entrypoints using the same mandatory owner, valid non-Team provider-managed flow, root→L1→L2→L3 and rejected L4, per-Team override isolation, untrusted/missing/malformed lineage, changing limits at each asynchronous boundary, duplicate IDs, provider replacement, external providers, multiwriter fencing, disk/process restart, interrupted publication and rollback. The current source evidence establishes blockers; it does not show these tests pass or justify deploying a central gate.
