# Team depth admission — bounded source WIP and proposed contract

**Status: BLOCKED for R1/R2 and cross-entry enforcement.** This is an experimental patch against public source commit `b830ec950faba0a46dda564be3e2d854afed94f1`, containing the earlier Team selection WIP as well as a narrow Team-only absolute-depth guard. It is not a native release, installable product, model-facing feature, relative Team budget, or GUI/E2E acceptance. It has not been deployed and installed rc.5 equivalence is unproved.

## What the source WIP actually changes

Team `spawnAdmitted` resolves the current Host global subagent max depth and passes the resulting absolute cap into `startActivation`. The existing native manager enforces it and requires a depth-capable provider. Missing cap or unsupported provider fails closed. A rejected spawn currently has an already-flushed provisioning entry which settles to **failed**, reserving the name; this preserves existing Team provisioning behavior but is not a pre-admission no-write guarantee. Parent/child depth continues to come from native session/header and Agent policy, not caller-provided depth.

The full pinned-source synthetic Host Team suite passed **54/54** and Team source TypeScript `--noEmit` passed. Real Loader configuration was changed 1 → 0 → 1: Team spawn failed at zero and succeeded with a depth-1 child at one. A provider without the native depth capability was rejected before its prepare method. Two intentional negative canaries demonstrate the remaining failure:

1. Direct `subagents.startActivation` without `maxDepth` succeeds while Host global max is zero. Workflow Host currently uses this uncapped route. This proves the Team-only guard can be bypassed by another entrypoint.
2. A Team spawn admitted at cap 1 and paused inside provider preparation can still succeed after the live Host cap is reduced to 0. The cap was snapshotted before the change, so an immediate revocation guarantee is not met.

## Proposed authoritative contract — not implemented

1. **Identity and authority.** The Host owns a durable Team-node identity and parent-child membership record. An exact live caller is resolved against authoritative committed lineage, not caller-supplied Team IDs, depth numbers, UI state or `AgentOptions.subagentDepth`. Each durable node identifies its Team root, parent Team node, owning session, creation epoch and authority. Absence, conflicting lineage, stale caller, incomplete recovery or a malformed record yields a typed `UNKNOWN`/denial; it must never default to an independent root. Ordinary non-Team delegation is distinguished by a trusted explicit scope rather than by missing metadata.
2. **Relative budget.** Each committed Team subtree has a root anchor depth and a policy revision. The effective budget must define how a team override interacts with the global default and all ancestor limits; the product spec requests root plus at most three levels and team-specific overrides, but does not fully specify whether an override can exceed the global default. Treat that choice as unresolved and do not implement one by assumption. A proposed safe rule is that each ancestor's remaining relative budget and the product hard ceiling apply simultaneously. A request is denied when any authoritative constraint would be exceeded; arithmetic uses validated non-negative safe integers and the child's actual lineage.
3. **One admission owner.** A Host-owned primitive—not a Team UI or individual tool wrapper—must gate Team spawn, ordinary subagent tool, direct `startActivation`, workflow children and every other path able to create a descendant in a Team scope. It receives the exact live caller and requested operation, resolves the Team scope and policy, and checks provider capability. If the scope cannot be proven or an external/provider-managed runtime cannot carry and enforce a verifiable budget, it denies rather than dropping the constraint. Non-Team provider-managed behavior retains its existing semantics outside a proven Team scope.
4. **Atomic policy changes.** Define a linearization point shared by policy updates and admission. Capture a versioned permit and revalidate it immediately before publishing a child/accepting a durable initial message, while a common authority serializes update and admission; on mismatch cancel/rollback partial work and do not report success. A proposed contract treats lowering as applying to admissions that have not reached that point, without silently killing already-published work. Cross-process owners require durable compare-and-swap or another proven single owner; an in-memory mutex alone is insufficient. Product confirmation is needed for the precise behavior of existing descendants and pending work.
5. **Durability and recovery.** Persist identity, Team ancestry, policy revision/override and an idempotent admission record atomically with the authoritative Team journal, or define a recoverable write-ahead state machine. After restart, reconcile all pending permits and provider outcomes before admitting new work. Unknown outcomes stay unknown; duplicate retries and partially created children are not assumed absent. Tampered, missing or conflicting history fails closed. Preset/model selection and other authorization are separate checks.
6. **External execution.** A local cap passed to an external provider is insufficient if the remote runtime can spawn independently. It needs authenticated policy propagation, non-forgeable scope, durable cross-process enforcement, cancellation and revocation semantics; otherwise Team-scoped use is blocked. Existing non-Team `provider-managed` behavior must not be silently replaced by a global absolute cap.

## Required tests before claiming enforcement

- Genuine Host tests for Team, workflow, direct, tool and provider-specific entrypoints using the same owner; root→L1→L2→L3 succeeds and L4 returns the typed error, including concurrent creation and nested Team identity.
- Global-default versus per-team overrides, sibling isolation, ancestor caps, missing/forged/stale identity, cross-realm and proxy inputs, unsupported providers, policy update/revocation races at every await and no leaked child or misleading durable success.
- Crash/restart, cold resume, partially written records, duplicate permits, concurrent processes, multi-owner fencing and recovery of unknown outcomes. Test current products' legitimate non-Team/provider-managed behavior unchanged.
- Real isolated product build, browser/transport path, settings UI, permissions, fixture and E2E gates remain separate. The existing exact-port localhost sandbox policy fails wildcard and non-loopback bind canaries and cannot be used as the network boundary.
