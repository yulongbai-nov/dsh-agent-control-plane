# Durable Team selection authority — unresolved design, default deny

This document is a source audit and proposed contract, **not** an implemented grant service or a user authorization. The existing `selection-authority-wip.ts` is an unauthenticated, in-memory synthetic experiment; it must not issue real grants or be installed. Its optional callback can be omitted by other Host entrypoints. The separate fail-closed Team selection WIP blocks explicit selection. No real app, profile or model was accessed for this audit.

## What the pinned source provides — and does not prove

- The Gateway carries an authenticated `Peer` principal and, in `packages/api/gateway/src/index.ts`, applies resource policy for non-owner principals; the owner path has a broad baseline. This proves a possible caller-identification seam, **not** a Team-scoped user-consent decision or that a model/tool cannot reach a proposed new endpoint.
- `SettingsController` exposes `@Remote` updates and optional `expectedRevision`; the settings implementation derives namespace revisions from observed configuration changes. A caller may omit that revision. Neither this generic API nor the existing snapshot proves a durable per-Team grant epoch, explicit user consent to a specific model/preset, or atomicity with child publication.
- `remoteAccess.allows()` deliberately returns true outside a Remote call or when the principal is absent. It must **not** be reused as a fail-closed test of an authenticated human issuer. An owner principal is not by itself a gesture or a choice to authorize a particular Team.
- `subagentModelSelection` samples its opt-in for newly composed Sessions; existing Session policies remain when the setting is later disabled. The frozen policy event records model routes, not a Team-specific revocation epoch or preset/maxTokens grant. Reinterpreting the switch as live revocation would silently change existing non-Team semantics.
- `storage-domain` offers a per-domain-instance write chain and durable backend writes, but that does not by itself prove a cross-process CAS or a transaction with Subagent publication. Its loader can quarantine malformed data and treat it as absent; for a grant system absent, malformed, quarantined, unavailable or ambiguous policy must all deny, not resurrect a cached grant.

## Candidate record and lifecycle — not implemented

One Host-owned versioned record per **verified** durable Team scope could contain `{version, teamRoot, teamEpoch, revision, state, routes, presetGrants, maxTokensPolicy}`. `state` has explicit active/revoked values, and allowed routes/presets are exact typed entries. A preset grant would identify the immutable preset revision/content, not merely a mutable name. Unknown versions, duplicate entries, missing team lineage, malformed or unreadable state return `UNKNOWN`/deny. A new installation or remounted service starts deny until the record and current issuer authority are loaded and validated. Root/session identity and Team epoch must come from the yet-unimplemented durable Team lineage owner, not a caller's Team ID or a model tool argument.

`issue`/`replace`/`revoke` require a separately designed, authenticated owner-facing action that records the exact scope and intended permission. A possible Remote adapter must require a present owner invocation, validate exact Team ownership, demand an expected revision, distinguish a direct user action from autonomous tool access, and fail if any of those cannot be proven. A trusted in-process API must not silently treat missing invocation as owner; it needs an unforgeable Host capability or another audited explicit authorization channel. The source audit did not establish such a capability, so the actual issuer remains **UNKNOWN** and no runnable issue/revoke endpoint is provided.

Durable revoke must be ordered with an admission coordinator at a common linearization point: lowering or revoking fences unpublished work, does not silently kill already-published children, and never reports a false successful denial after an unknown write. Take a revisioned permit after reading exact live policy; perform adapter/model/preset preflight without holding long global locks; immediately before actual publication revalidate exact Team, grant revision, provider/preset identity and cancellation under the same authority that serializes policy updates. Cross-process use needs proven storage CAS/fencing; a per-instance JavaScript queue and post-read comparison are insufficient. Untrusted or external providers that can start work outside that boundary are denied unless they implement an independently verified contract. Cleanup, durable failed provisioning and partial provider side effects must be recorded honestly.

## Required tests before an allow path

1. Owner vs non-owner vs missing invocation, model/tool attempts to issue/revoke, direct Host bypass and Team mismatch; no provisioned child or persisted grant on denial. Test the actual transport and scope, not just a supplied `owner` boolean.
2. Two Teams with independent revisions; opt-in and exact route/preset grant; unknown provider/capability/effort/maxTokens; replacement and revoke during every asynchronous preflight/materialization boundary; unchanged inherited and non-Team `provider-managed` behavior.
3. File/backend failure, unknown receipt, duplicate issue, stale expected revision, concurrent update and competing process; restart and cold Team reconstruction with valid, missing, malformed, stale and revoked records. Prove an old grant cannot reappear after revoke.
4. Preset replacement/unload during preflight and creation, route adapter replacement, cancellation and rollback; provider startup may already have side effects before the final local admission, so measure those separately.
5. Verify all relevant Team/tool/workflow/direct entrypoints and actual publication cutoffs. Until these and installed artifact/security gates pass, model-facing Team route/preset fields remain absent and direct explicit selections remain denied.
