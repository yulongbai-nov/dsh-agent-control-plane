# R4 candidate preview — blocked before creation

**Not automatic team creation or R4 acceptance.** This isolated source WIP targets pinned public source `b830ec950faba0a46dda564be3e2d854afed94f1`. It is not installed or registered as a user-facing API. No real app, profile, user Session, external model, browser or service was intentionally accessed.

`TeamSuggestionWip` accepts an already supplied **untrusted candidate list**, not an LLM-generated suggestion or task-derived plan. It validates 2–5 unique bounded name/description records, rejects extra model/preset/provider fields, getters, Proxies and control characters, checks the exact live Agent is the Team Lead and that the pinned fresh local `spawn` provider advertises depth support, and returns a detached frozen preview. Draft handles are owned by the exact live Agent object; cancel invalidates that handle for this process. Preview, cancellation and confirmation make no Team member/task or activation calls. `confirm()` **always returns BLOCKED** for an active draft because a trustworthy human-confirmation seam for the exact plan has not been established; a cancelled draft returns CANCELLED. No boolean, caller flag, model output or generic owner Peer is treated as human consent. The helper keeps an ephemeral in-memory draft; cancellation is not durable and cannot undo a created team because this WIP cannot create one.

These bounds and backend checks are not a full authorization, route/preset capability or Team recursion proof. A backend may change after preview; a real implementation must revalidate exact provider identity, scope, permissions and limits at commit. Agent identity lookup assumes a genuine trusted Host Agent, not an arbitrary hostile Proxy. A caller-supplied role description remains untrusted presentation content. There is no task analysis, recommendation engine, UI, actual human confirmation, one-click creation, per-member model/preset, durable transaction or rollback. Explicit model/preset selection and shared depth/archive gates remain independently blocked.

## Why confirmation remains blocked

The pinned `dsh-user-approval` service's `request()` requires an open Agent turn and appends `approval/asked` **before** awaiting an answer, then appends `approval/decided`; its answerer may be a UI or an ACP client, and absence/cancellation fail closed. This can be a useful audited approval mechanism, but the audit has not established that it presents the complete exact frozen Team plan to a human, binds approval to Team/actor/plan version, or rules out machine answerers. It also performs Session audit writes before the answer, which must be reconciled with the requested no-side-effects-before-confirm condition. Do not reinterpret `allowed-once` as plan-specific human consent without those proofs.

To implement R4, define and test: (1) explicit human review/confirmation bound to a canonical plan hash, exact Lead/Team authority and provider/model/preset grants, with cancellation/expiry and no mutation before the agreed boundary; (2) bounded task-derived candidate generation, provenance and untrusted rendering; (3) durable plan execution with per-member receipts, partial failures, retries and an honest reversible/undo policy; (4) interaction with shared depth, archive and selection admission, provider replacement, revocation and crash recovery; (5) actual isolated UI/Host/transport tests. Until these exist the correct state is BLOCKED, not a claim that auto-created teams or undo work.
