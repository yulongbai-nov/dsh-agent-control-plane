# Canonical task-title format evolution — design only

**No V5 implementation, migration or rollback exists here.** The current WIP's task-source `session/title` event violates released V4 validation and can make a real Session unreadable. Do not install it. This document records a candidate design and narrowly scoped reader evidence, not permission to write data or proof of compatibility with the installed app.

## Candidate V5 contract

- Introduce a new **required** task-title event or a new versioned payload of `session/title`, never forge `user/message` references or call the user-unpinning `refresh()` path. It must record task title, exact Lead session identity, exact task identity/revision, exact source-event sequence and a versioned immutable digest/canonicalization scheme. A digest is an integrity aid, not authentication or proof of permission. Decide whether the task label is deterministic text or generated, and specify ties, ambiguous tasks, deletion and stale-source behavior.
- A Host-owned acceptance authority must validate exact live child/Lead identity, user authorization and revocation epoch, complete task-source cut, owner and task revision. The title service must serialize user pin, ordinary provider result and task update on the same local revision/abort path, and recheck authority/source/cancellation and pin in the synchronous acceptance boundary. Cross-session logs are not an atomic transaction by default; add a durable source watermark/admission protocol or explicitly document and test bounded eventual consistency. Unknown, malformed, unauthorized, cold or unverifiable source means do not update.
- V4 → V5 migration should preserve all old title events and their ordering unchanged, never infer a task provenance from message sequences or titles. Older pins remain pins; old fallback and provider sources retain their original meanings. Mixed historical cases, forks, inherited-event counts, sequence mappings, ignorable records, aborted writes and source-unavailable cases require explicit codec/validator and migration tests. V5 parser must validate its own source shape and safe integer bounds; merely expanding `SessionTitleSource` is insufficient.
- Freeze the authoritative version decision only after reviewing the full codec, every released reader, plugin records, downstream UI and `SESSION_FORMAT_VERSION` contract. V4's `ignorable:true` applies to unknown **event types**, not a new `source.kind` nested in the existing known event. A separate ignorable informational overlay can degrade to the old canonical title, but it does not itself provide canonical R9 title behavior.

## Older-reader and rollback evidence

Pinned public source `session-format/src/catalog.ts` rejects a newer generation before decoding it, and `session-persistence-jsonl/src/index.ts` classifies `sourceVersion > SESSION_FORMAT_VERSION` as unsupported. A synthetic test in `v5-reader-probe.patch` created a well-shaped V5 header in a temporary JSONL generation and observed the pinned V4 persistence code return `SessionFormatUnsupportedError` on **both read and write opens**, with the original synthetic file byte-identical after each refusal. One test passed; retained `work/title-evidence/v5-probe.log` SHA-256 `d99ec5eedf09c9f595aac77dd947a3ea0b939c3cc2fe6493f82d8fa20e3aa590`; probe patch SHA-256 `cbaed58328a3cb1da191da69cf956e753fa0073aa0ae9e4bf7f184e151533e9a`. The patch was checked against the pinned base and is test-only. This is not a genuine V5 codec, migration, installed-binary test, torn-tail test, mixed-generation test or evidence about every reader.

Rollback cannot be described as simply reopening the V5 Session with V4: older readers will refuse it. Before any future upgrade, an authorized operator would need a consistent, independently verified V4 backup and an approved recovery procedure. Restoring that backup after new V5 writes discards or separates later work; preserve the V5 generation and changes, make the loss and reconciliation explicit, and never silently truncate, overwrite or repair it. A reverse migration is a separate feature requiring a documented loss model and proof that unsupported task events can be dropped or exported without falsifying pins, lineage or authorization. Concurrent writers, crashes between generations, stale locks, unknown source and failed rollback must be tested using disposable synthetic stores first.

## Required work before implementation

1. Establish a legitimate Team-source/child-authority seam, immutable identity and task observation order, plus permission revocation and late-event handling. No trusted authority implementation currently exists.
2. Agree semantics for user pins, provider/task ordering, idle titles, multiple active tasks and unauthorized or missing Lead state. Define cancellation and the linearization point around all title writers.
3. Design V5 codec and a contiguous V4→V5 migration, schema validation and reader registration; test source V4 remains intact until successful publication, full replay, forks, crash boundaries, corrupt/incomplete input, concurrent writers and old-version read/write refusal. Test explicit restoration from a backup without overwriting newer work.
4. Establish signed artifact provenance, isolated Host/renderer and real E2E path. This design and current synthetic tests are not R9 acceptance.

## Concrete implementation map and stop point

The public pinned source's writer version is `packages/core/session/src/types.ts:SESSION_FORMAT_VERSION = 4`; `packages/session/session-format-catalog/src/generated.ts` is generated from migration package declarations by `scripts/gen-session-format-catalog.ts` and currently assembles codecs 0–4 plus adjacent edges. A real implementation would need, together:

1. A reviewed `session-format-v4-to-v5` package with a V4 source codec, V5 target codec/header validator/restorer, adjacent `4 → 5` migration declaration and package metadata; update the current Session format constant and regenerate rather than hand-edit the catalog. The migration should leave accepted V4 event meaning, event sequence, fork cut, pin and human-message references intact; unknown ignorable records stay opaque. Preserve V4 validation unchanged. The exact V5 event schema is not frozen.
2. A new V5 required task-title event, or explicitly V5-scoped known-event payload, with strict typed fields. It would be a log-only title proposal carrying Lead identity, task ID, task revision, event sequence, immutable task subject/cut and a well-defined digest algorithm/version if a digest is used. Reject missing, malformed or conflicting provenance. A digest by itself cannot show that the Lead log was authorized, complete or durable.
3. Extend the title projection, replay and single service-owner state so existing user pins survive migration and take precedence over all automatic task/provider changes. A user unpin must be an explicit established action; task observations cannot call `refresh()` and cannot fabricate a human message. Define deterministic arbitration for later user messages, task transitions, multiple tasks, archived/deleted/reassigned owners and recovery **before** fixing event shape. Historical V4 fallback/provider/user events must preserve their old interpretation.
4. Add an authoritative verifier and durable cross-log protocol before enabling the writer. The child event must not claim a Lead event is current merely because a caller submitted an ID or digest. The verifier must prove authorized exact identity and source durability/cut, preserve monotonically ordered revisions across service restart, and fence concurrent process writers; missing Lead, incomplete history, stale cuts, revoked permission and unresolved crash outcomes remain unknown. The product has no demonstrated such seam yet.

**Implementation stops here:** neither legitimate task authority nor cross-log atomicity/recovery is established, and deciding canonical priority and rollback loss semantics would be inventing product policy. Consequently no V5 version constant, codec, migration, event writer or user data was changed. This is a design blocker rather than a passing migration test.

## Required disposable tests for a future V5 implementation

- Starting from synthetic V4 generation, read-only migration must preserve the original bytes; write-open must publish a separately verified V5 successor without overwriting V4. Check exact user pin/fallback/provider title, sequence/cut and ignorable plugin record equivalence, repeated open, concurrent writers and source drift at every publication phase. Inject errors/crashes before and after durable publication; do not treat a retained V4 generation as automatic fallback.
- Test V5 task title write, flush, process teardown, fresh-process read and cold reattachment, user pin before/after task, explicit unpin, provider and task races, cancellation, same/different Lead revisions, stale/replayed events, absent or unauthorized source and authority revocation. Verify no fabricated human messages. Test both policy updates and source changes across each await, and show deterministic fail-closed behavior.
- Exercise true V4 binary read/write against new V5 generations (including mixed V4+V5 and torn/incomplete files) and prove it refuses before mutation or tail repair. The current V5-header probe only checks pinned V4 source with a simple valid header; it does not cover these cases or the installed distribution.
- Rehearse backup restoration only in a separate disposable root. Preserve V5 data and enumerate writes made after the backup; verify explicit user-approved loss/reconciliation. Do not rename or delete an actual newer generation to force fallback. Reverse conversion requires its own defined and reviewed loss model.
