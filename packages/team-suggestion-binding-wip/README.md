## Trust boundary still missing

The pinned Gateway authenticates owner Peers, but `PeerScope` represents principal kind and interaction capability, not whether a request originated from a specific trusted UI action. A synthetic authenticated Node client has already answered a generic approval-shaped Gateway event without a browser. Therefore a Remote endpoint that accepts an owner token, plan ID, or caller-supplied `ui:true` cannot establish the requested distinction between trusted UI, model and ACP. This is about a **trusted client capability boundary**, not an attempt to detect a physical person.

Candidate design: a separately named confirmation capability only the trusted UI host can invoke, never exposed to Agent tools or ACP, with a Host-issued one-shot opaque nonce bound to a canonical complete plan, exact live Team/Lead epoch, task revision, effective roles/providers/models/presets/limits, authority revision, expiry and cancellation. The trusted UI must present exactly that frozen plan; the Host validates issuer capability and all versions at the common durable creation boundary. UI reload, disconnected/stale Peer, replay, plan mutation, revoked permission, missing provenance and any uncertain write must deny. A native Electron-main channel restricted to the correct `webContents`/frame is a possible direction, but sender checks alone do not prove model/ACP cannot invoke the exposed bridge or synthesize an action; CSP, preload exposure, ownership and tool capabilities require actual source and integration review. No such enforced channel or end-to-end proof exists yet, so the source WIP continues to block confirmation rather than invent one.
