# WIP: process-local terminal attempt observations

**Research patch only; not an installable plugin, R15/R16 completion, or a trusted run/source receipt.** `upstream.patch` targets public DeepSeek Harness commit `b830ec950faba0a46dda564be3e2d854afed94f1`, not the installed app. Do not apply it to a real profile or deployment. The public source and installed rc.5 are not proven equivalent.

A synthetic Host characterization against the pinned public source showed two hazards: an around-dispatch wrapper can temporarily change `exec.callId` and `exec.arguments` before calling the terminal body, then restore the original values before the final `tools/result` observer; and one ingress call can invoke `next()` twice, resulting in two terminal bodies but one final result. Therefore a tool-side `callId → runId` record or a final-result observation alone is not reliable provenance.

The candidate adds an opt-in synchronous `ToolRuntime.observeTerminalAttempts` observer. At runtime ingress, before pre/around wrappers, the registry privately freezes the caller-supplied call ID, root call ID, requested name and registry-minted opaque execution token. Immediately before each actually resolved terminal body it emits a frozen process-local observation with that same ingress snapshot, the effective resolved name, and a per-execution ordinal. Short circuits and pre-aborted calls emit no terminal observations. It does not include argument payloads. The caller may have supplied a forged call ID; the snapshot is **not** bound to a Session `tool/call` event. `originEvent`, `acceptedInit`, and `durability` are explicitly `unknown` on every observation. Tokens are process-local Symbols, not durable IDs. No `runId` or job association is made.

**Limits and risks:** observations are live-only and opt-in; subscribing late or callback failure can lose coverage. There is no persisted admission receipt, durable cursor, attempt→run/job handoff, immutable engine-consumed init, authorization, child token attribution, crash recovery, or cross-process proof. A subscriber has access to potentially sensitive identifiers; exposure requires separate authorization. Only trusted synchronous observers are allowed: synchronous throws are contained, but observers can block, reenter, perform side effects, or return a rejected Promise; the prototype does not sandbox them or guarantee asynchronous rejection containment. It preserves current wrapper mutability rather than claiming to enforce TypeScript readonly at runtime. Additional side effects, multi-listener ordering, future API compatibility, and performance require review before any release.
