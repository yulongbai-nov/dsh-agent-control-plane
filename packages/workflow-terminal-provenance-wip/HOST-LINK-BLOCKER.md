# Terminal attempt to consumed Workflow init: source-backed blocker

This is an audit of the public pinned source `b830ec950faba0a46dda564be3e2d854afed94f1`, not proof about the installed application. No new runnable receipt, production provenance or E2E claim is made.

The ToolRuntime WIP records a registry-minted process-local ingress token and ordinal immediately before each resolved terminal `tool.execute`, without adding a privileged capability to the executed tool or engine. Wrappers can suppress the terminal body (zero observations), invoke `next()` once or repeatedly (one or more observations), and temporarily mutate execution fields. Concurrent `next()` calls can overlap. Observing an ordinal and a later Workflow event by order, ID, name, time or mutable execution fields cannot establish which body owns which run. No current private binding ties one terminal attempt to the Workflow tool's particular `workflowEngine.start` call.

The pinned `PtcWorkflowEngine.start` parses `request.script` and later reads it again for `WorkerInit`; other request properties and synchronous callbacks likewise sit between validation and materialization. `PtcWorkflowRun` holds the init and its `begin` binding returns a fresh `snapshotJsonValue` each time. The guest awaits `host.begin` and constructs `WorkflowExecution` from that response, but the Host has no authenticated, versioned acknowledgement tying a particular delivered response to guest consumption. A test double or failing runtime can invoke `begin` without a real guest consuming it; multiple begin responses can differ. A start event, run ID, returned binding response, or eventual result alone is insufficient to assert consumed init. Cancellation or worker crash before acknowledged delivery remains UNKNOWN; a durable journal is also absent.

A credible future design needs a source-owned, unforgeable per-terminal-attempt capability carried by the exact trusted Workflow tool invocation into the engine, not a user field or observer correlation. It must distinguish concurrent/multiple terminal invocations, retain immutable effective init after all validation, define the atomic boundary and content admitted to the actual transport/guest, identify and authenticate the runtime implementation, and report zero, one or multiple acknowledged deliveries without inventing consumption. Wrapper mutation, reentrancy, multiple `next`, abort before/after admission, transport failure, cancellation, crash/restart, bounded snapshots, authorization and durable receipts need dedicated source-backed tests and a precise semantic contract. It must also bind trusted session/call origin and consent; an ingress snapshot of a caller-supplied ID is not that proof.

No safe implementation can derive the requested consumed-init linkage from the current public observer and binding interfaces alone. Adding a fake flag or test-only acknowledgement would hide rather than resolve this gap. The existing pinned-source characterization remains useful but all unproved links must stay UNKNOWN.

## Pinned PTC transport boundary

The real Node PTC runtime owns a length-prefixed `JsonChannel` on the subprocess control pipe. The child sends a monotonic numeric binding-call ID; the Host validates it, resolves the named binding, calls it, and sends a matching `reply` frame. Those IDs identify generic binding RPCs within one worker, not ToolRuntime terminal attempts. A successful Host channel write only establishes that a reply was handed to the transport, not that the guest deserialized it, constructed `WorkflowExecution`, or used it. The actual guest awaits `host.begin({})` before constructing `WorkflowExecution`, but sends no dedicated authenticated post-construction acceptance receipt to the Host. Ordinary progress or terminal frames do not independently bind the exact `begin` response or prove a particular origin. Other `PtcRuntime` providers can implement the seam differently, and the generic binding reply exposes no private ToolRuntime attempt capability. Thus the existing control pipe cannot establish the requested end-to-end association without changes at the registry/tool/engine seam and an explicit versioned runtime/guest acknowledgement contract. A future acknowledgement must itself specify trustworthy worker/bootstrap identity, exact immutable response digest, replay and multiple-begin behavior, and transport/crash ambiguity; receipt delivery alone is not durable commit.
