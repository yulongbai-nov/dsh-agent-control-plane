## Why persistent overrides remain open

The older standalone session-tree stores a global JSON object under `dsh-session-tree.avatar-types.v1` keyed only by session ID in browser localStorage. That design has no demonstrated Host/principal/workspace authority boundary or revocation-generation fence. Reusing it here could retain or display a preference associated with a formerly accessible identity, or collide when an ID is reused. Hashing IDs does not prove access or prevent correlation. No existing durable storage is read, migrated, overwritten, or cleared by this candidate.

A viable durable design needs a Host-issued, stable scoped identity and independently authorized reads/writes for each preference (including workspace, principal and session generation), denial and reset fencing for in-flight reads, and explicit cross-device and retention/delete policy. Browser storage alone cannot authenticate the principal; a secure host service would need to validate caller scope at request and delivery time. Before implementation, specify what happens on revocation, regrant, logout, principal/Host switch, session deletion/recreation, and account synchronization; do not show old values while scope is unknown. Adopt a versioned schema and conflict/atomicity policy; surface quota, unavailable, corrupt and concurrent-write errors without replacing prior data. Custom PNG support additionally needs bounded file/decoded size, safe decoder/error handling and lifetime management. Tests must include two principals/workspaces with reused IDs, late responses after reset, reconnect/regrant, storage corruption/quota and concurrent changes, image failures, refresh, screen-reader/keyboard, and actual Host/client authorization. None of that persistence or authorization is implemented or proven here.
