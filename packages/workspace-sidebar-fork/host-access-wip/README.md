# WIP: narrow host-side catalog access mitigation

**Not installable and not a complete privacy boundary.** `catalog-access.patch` is a candidate against public DeepSeek Harness source commit `b830ec950faba0a46dda564be3e2d854afed94f1`; it is not an installed-app patch, product build, or proof that the public commit matches the user's installed rc.5. It is intended only for a disposable synthetic checkout with reviewed dependencies. Do not apply it to the installed application or a real user profile.

A synthetic non-owner Gateway test against that public source demonstrated that a parent `session/projections` grant disclosed its `subagentCatalog` child's ID, label, mode, and creation time while direct child `session/projections` was denied. A characterization assertion passed and a privacy assertion failed (1 passed, 1 failed; 7 unrelated cases skipped). No real session, installed DSH app, or network was used.

The candidate filters `subagentCatalog` in `session/projections`, `session/control` baseline and incremental frames, and follow-opening projections using same-action Session grants for each child. Parent `session/page` and `session/follow` reject pages or frames containing a denied `subagent/catalog` event instead of removing events and silently breaking sequence continuity. The denial has a generic reason and no child ID. Owner and trusted in-process calls preserve original behavior; duplicate visible entries and native direct-parent/mode checks are preserved. This is intentionally fail-closed and may deny an entire shared parent history where native upstream allowed it.

**Remaining blockers:** `remoteAccess` bypasses checks for owner/trusted in-process callers; it is not a local collection authorization contract. Other event types, arbitrary messages, projections, or `SessionSummary.parentSessionId` may expose related identities; this patch does not classify them. Cross-workspace identity/ownership is not established. Access revocation does not itself re-emit `session/control` catalog values, so a client may retain previously delivered metadata; no retraction or cache invalidation design is implemented. Denied parent history may impair continuity and usability. External entries and missing/malformed facts are conservatively hidden or denied. These limits prevent a production privacy or R7 E2E claim.

## Reproduction and evidence

1. Obtain a **fresh, separate** checkout of public upstream at the full commit above and verify its HEAD and a clean target tree. Prepare a reviewed, compatible dependency installation separately; no dependency installation is part of this patch.
2. Run `git apply --check` with `catalog-access.patch` against that checkout and review the diff before applying it to that disposable checkout. Never apply it to the installed app.
3. With the checkout's reviewed Vitest and Node 24, run the two scoped synthetic files `packages/api/session-controller/tests/remote-access.host.spec.ts` and `packages/api/session-controller/tests/r7-synthetic-catalog-mitigation.host.spec.ts`, with a dedicated synthetic `HOME`/`TMPDIR`. The latter is included in the patch. Do not run arbitrary upstream scripts or real profiles to reproduce this check.
4. In the prepared test checkout, the two files passed **13/13** synthetic tests: 7 existing access tests and 6 candidate tests covering parent-only and absent grants, child-only authorization, owner, duplicate entries, Gateway control stream, parent page/follow, and incorrect direct parent. The `session/follow` characterization uses an in-memory invocation context; the `session/control` baseline also traverses the synthetic Gateway wire-stream interface. The output log was retained separately in the working evidence directory as `r7-host-catalog-after.log`.
5. The pre-existing pinned public checkout accepted `git apply --check`. A forced TypeScript 6.0.3 project-reference build in the prepared checkout passed after adding `catalog-access.ts` to the Host tsconfig files list. This does not prove a complete release build, installed-app equivalence, or real E2E.
